# Releases and versioning

Imp uses semantic-release to publish releases automatically from `main`.

Published releases are listed on the repository's GitHub Releases page.
Historical milestone tags are not part of version calculation.

## Version semantics

Release impact is determined from Conventional Commits since the most recent
`vX.Y.Z` release tag:

| Commit                                      | Release impact  | Example from `0.2.1` |
| ------------------------------------------- | --------------- | -------------------- |
| `fix:`                                      | patch           | `0.2.2`              |
| `feat:`                                     | minor           | `0.3.0`              |
| `type!:` or `BREAKING CHANGE:`              | major           | `1.0.0`              |
| `docs:`, `test:`, `chore:`, `ci:`, `build:` | none by default | remains `0.2.1`      |

Pre-1.0 versions follow normal SemVer increments. In particular, a normal
`feat:` while Imp is `0.x` does **not** mean the project is ready for `1.0.0`.
For example, `feat:` after `0.2.1` produces `0.3.0`.

Do not mark a change as breaking merely because it is substantial. Use `!` or
a `BREAKING CHANGE:` footer only when the change is actually incompatible with
the supported public behavior or interfaces.

Do not choose or edit release numbers manually.

To preview what the current commit history would release, use:

```bash
npm run release:next
```

This is only a local preview. It does not create or publish a release.

## Automatic release process

Release publication requires no maintainer command after an eligible change is
merged to `main`.

On a push to `main`:

1. the normal CI gate runs;
2. after that gate succeeds, semantic-release examines commits since the latest
   release tag;
3. if there is no release-relevant change, the release job exits without
   changing the repository;
4. if a release is required, semantic-release calculates the next version and
   generates the release notes;
5. the release prepare hook updates all release version locations and
   `CHANGELOG.md`;
6. CI creates and pushes a signed release-metadata commit;
7. semantic-release creates and pushes the signed annotated `vX.Y.Z` tag; and
8. the Release workflow checks out that tag, verifies it, builds the Windows
   installer and Linux server bundle, and publishes the GitHub Release.

The release-metadata commit uses a message such as:

```text
chore(release): 0.2.0 [skip ci]
```

It is generated by automation and is not a new release input.

## Signing

Automated release commits and version tags are SSH-signed with a dedicated Imp
release key whose private half is stored in the repository's GitHub Actions
secrets. The corresponding public key is committed at
`.github/release-signing-key.pub`.

The automation key is separate from maintainers' personal signing keys.

The Release workflow cryptographically verifies the annotated version tag
against that public key before it builds or publishes artifacts.

Do not create `vX.Y.Z` tags manually.

## Recovery

The release automation is recoverable without replacing a published tag.

If preparation pushed the signed release-metadata commit but tag creation
failed, manually dispatch the `CI` workflow on the current `main` branch. The
release job then reuses the prepared release after verifying its version,
generated notes, commit message, and signature.

If the version tag was successfully created but artifact building or GitHub
Release publication failed, rerun the `Release` workflow for that existing tag.
Do not create a replacement tag or manually change the version.

## Release invariants

- Release versions come from Conventional Commit semantics, not from slice
  numbers, milestone tags, or subjective estimates of change size.
- `feat:` means a minor SemVer increment. From `0.2.1`, that is `0.3.0`.
- Only an explicitly breaking change produces a major increment.
- A successful eligible merge to `main` is sufficient to start release
  automation; no release command is required from a maintainer.
- `npm run release:next` is an optional preview only.
- Version files and generated release notes are updated by release automation.
- Final `vX.Y.Z` tags are annotated and SSH-signed.
- Do not create release tags or choose release versions manually.
- Do not give a maintainer's personal signing private key to GitHub Actions.
