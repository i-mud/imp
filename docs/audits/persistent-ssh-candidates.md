# Persistent SSH transport candidates (Slice 29.3b)

**Decision: use russh for the isolated experiment, not as an approved Guided transport.** Native Windows OpenSSH does not offer the Unix `ControlMaster` interface. An embedded SSH client can expose channels directly on both platforms, but it does not inherit the player's OpenSSH trust, identity, or routing policy. A successful pinned-key fixture would not justify replacing Managed or External SSH.

The [29.3a audit](guided-ssh-forward.md) exercised warm `ssh -L` and a new `ssh -W` process per connection against a disposable Linux sshd, from Linux under WSL2 and native Windows. The latter held `/state` and delivered 20 exact-context actions, but repeatedly authenticated, took longer, and failed the server-first half-close check that `-L` passed. Neither test exercised Unix multiplexing or either embedded library. The comparison below is based on upstream docs and source, not runtime acceptance of the candidates. WSL2 or a Windows cross-build is not native Windows runtime evidence.

## System OpenSSH multiplexing

- **Linux/Unix and native Windows.** Unix `ControlMaster` shares an authenticated connection over a `ControlPath` socket. A foreground, application-owned `ssh -N` master can stay warm with `ControlPersist=no`; `ControlPersist` is the option that lets a master outlive its initial session in the background, not a prerequisite for reuse. [`ssh -W` and `-O` controls](https://man.openbsd.org/ssh) have different contracts. The mux protocol's [stdio forwarding request](https://github.com/openssh/openssh-portable/blob/master/PROTOCOL.mux) passes stdin/stdout file descriptors to the master; `-O proxy` instead proxies SSH connection-protocol packets, requiring a channel-protocol client, not just a byte pipe to the relay. `-O forward`/`cancel` manage actual forwards, not private streams. The Win32 port [lists client ControlMaster as unsupported](https://github.com/PowerShell/Win32-OpenSSH/wiki/Project-Scope), [explains the descriptor-passing gap](https://github.com/PowerShell/Win32-OpenSSH/wiki/About-Win32-OpenSSH-and-Design-Details), and [tracks it as open](https://github.com/PowerShell/Win32-OpenSSH/issues/1328). Accepting the option, having a Windows `ssh-agent`, or running WSL does not provide native mux support.
- **Host trust, identity and routing.** The master retains the installed client's [`ssh_config` behavior](https://man.openbsd.org/ssh_config): opt in to fail-closed `StrictHostKeyChecking=yes`, known-hosts files and applicable host CA/revocation policy, explicit identity files, agent, encrypted keys through an agent or a supported prompt, user certificates, `Host`/`HostName` aliases, explicit or configured port, and `ProxyJump`/`ProxyCommand`. With `BatchMode=yes` there is no interactive passphrase prompt. Jump hosts have their own authentication/trust and configuration; compatible features depend on the actual client build. Windows has [its own OpenSSH agent service](https://learn.microsoft.com/en-us/windows-server/administration/openssh/openssh_keymanagement), independent of mux. Joining a master does not authenticate again or retroactively apply a new trust/identity policy. Config must be trusted: `ProxyCommand`, `Match exec`, and other options can run local programs.
- **Streams and ownership.** A private foreground master plus `-W` slaves avoids a local TCP data listener on Unix, but still needs a helper and pipes per stream. An unusable control socket can make ordinary `ssh -S … -W …` fall back to a fresh connection ([`muxclient` and caller](https://github.com/openssh/openssh-portable/blob/master/mux.c), [`ssh.c`](https://github.com/openssh/openssh-portable/blob/master/ssh.c)); a separate `-O check` does not guarantee reuse. Treat the mux's full-duplex, EOF in both directions, backpressure and cancellation as unmeasured through those pipes. An ownership design would need a per-run socket in a user-private directory, no attachment to a user's master, explicit fail-closed channel admission, slave cancellation without killing sibling streams, bounded master/proxy-tree teardown, and tests for owner death. `-O stop` stops accepting mux clients, not the master itself; closing a slave's input is not session shutdown.
- **Distribution.** Using the installed executable adds no linked SSH dependency to Imp; availability, version, and patching follow the OS or package provider. Native Windows availability varies by OS/installation ([Microsoft overview](https://learn.microsoft.com/en-us/windows-server/administration/openssh/openssh_overview)). Bundling it would be a separate packaging/security-maintenance decision under the upstream [collection of permissive licenses](https://github.com/openssh/openssh-portable/blob/master/LICENCE), and would not add missing native mux support.

## russh (selected for the experiment)

- **Linux and native Windows.** [`connect`/`connect_stream`](https://docs.rs/russh/0.65.4/russh/client/index.html) and [`Handle::channel_open_direct_tcpip`](https://docs.rs/russh/0.65.4/russh/client/struct.Handle.html#method.channel_open_direct_tcpip) use Tokio sockets/streams rather than a platform mux or an `ssh` subprocess. One authenticated SSH session can carry separate relay channels for the held state connection and short action connections. This API shape supports the experiment on both platforms; it does not establish native Windows behavior.
- **Host trust.** [`Handler::check_server_key`](https://docs.rs/russh/0.65.4/russh/client/trait.Handler.html#method.check_server_key) rejects by default. A valid key-exchange signature proves possession, not that the key belongs to the intended endpoint. The experiment should accept only the exact, independently generated and provisioned raw Ed25519 fixture host key, bound to its explicit SSH endpoint; reject other keys and host certificates, with no trust-on-first-use or file updates. The [known-hosts helper](https://docs.rs/crate/russh/0.65.4/source/src/keys/known_hosts.rs) is not an implementation of OpenSSH's full trust policy, including host CA/principal checking, revocation, `HostKeyAlias`, and system/user trust precedence. Do not market a pin-only flow as a compatible substitute for those controls.
- **Identity and routing.** The [keys](https://docs.rs/russh/0.65.4/russh/keys/index.html), [auth](https://docs.rs/russh/0.65.4/russh/client/struct.Handle.html) and [agent](https://docs.rs/russh/0.65.4/russh/keys/agent/client/struct.AgentClient.html) APIs expose private-key loading with a supplied passphrase, OpenSSH _user_ certificate auth, and agent signing (Unix sockets; Windows named pipe or Pageant). These are building blocks: no automatic discovery/selection or prompt flow, and format/algorithm availability depends on the build. An explicit SSH host/port is straightforward; `connect_stream` could carry another SSH connection over a separately authenticated hop. It does not resolve OpenSSH aliases, interpret the player's config, or apply `ProxyJump` or each hop's trust policy. The experiment uses a generated fixture identity only and exercises none of these optional integrations.
- **Streams and ownership.** [`Channel::into_stream`](https://docs.rs/russh/0.65.4/russh/struct.Channel.html#method.into_stream) gives an async reader and writer. SSH flow control is per channel; the [stream writer's shutdown](https://docs.rs/crate/russh/0.65.4/source/src/channels/io/tx.rs) sends EOF, not CLOSE. The receive side must remain alive to deliver post-EOF data. A drop-triggered CLOSE is not proof of completed cleanup. The owner must bound queued data and admitted channels and retire a cancelled channel without tearing down unrelated streams; session loss must invalidate all its streams and pending work. One TCP connection still shares network loss, and per-channel windows alone are not evidence that an undrained stream cannot stall sibling work. Check both EOF orders, simultaneous traffic, stalled upload and download with another channel still progressing, cancellation during channel open and transfer, and bounded disconnect/owner death. Never replay an ambiguously sent action.
- **Dependencies, custody and updates.** The [exact `0.65.4` package](https://docs.rs/crate/russh/0.65.4/source/Cargo.toml) is Apache-2.0 and requires Rust 1.89. The test crate selects `ring` with russh default features disabled (no default AWS-LC, compression or RSA features); [ring has native build inputs and notices](https://github.com/briansmith/ring/blob/main/BUILDING.md). No external `ssh` binary is needed for the candidate client; an sshd is still needed at the other end. The isolated crate is not a desktop distribution change. RustSec lists [2026-0492](https://rustsec.org/advisories/RUSTSEC-2026-0492.html) patched from 0.63.1 and [2026-0493](https://rustsec.org/advisories/RUSTSEC-2026-0493.html) from 0.61.1; 0.65.4 meets the patched ranges of [all russh entries listed at review](https://github.com/RustSec/advisory-db/tree/main/crates/russh). That is not a transitive dependency audit. Embedding SSH would make Imp responsible for auditing the resolved graph, shipping patched binaries, and controlling how decrypted keys, agent access, and trust data are obtained, retained and kept out of logs. Fixture keys stay disposable; do not touch real keys, agents or SSH files.

## libssh2 (alternative)

- **Linux and native Windows.** [libssh2 1.11.1](https://github.com/libssh2/libssh2/releases/tag/libssh2-1.11.1) documents [`channel_direct_tcpip_ex`](https://libssh2.org/libssh2_channel_direct_tcpip_ex.html) on an authenticated session, with an [upstream forwarding example](https://libssh2.org/examples/direct_tcpip.html) including a Win32 socket path. The caller opens the SSH socket and selects the port. A Rust build could use [`ssh2`](https://docs.rs/ssh2/latest/ssh2/); neither the API nor the example verifies Imp's use on either platform.
- **Host trust, identity and routing.** Get the negotiated key with [`session_hostkey`](https://libssh2.org/libssh2_session_hostkey.html) and enforce an explicit pin or use [`knownhost_checkp`](https://libssh2.org/libssh2_knownhost_checkp.html) with an explicit policy; reject mismatch, no match and errors. File parsing/checking is not full OpenSSH trust or host-certificate policy. [`userauth_publickey_fromfile_ex`](https://libssh2.org/libssh2_userauth_publickey_fromfile_ex.html) takes a private-key file and passphrase; the pinned release's [`userauth.c`](https://github.com/libssh2/libssh2/blob/libssh2-1.11.1/src/userauth.c) recognizes OpenSSH user-certificate key types, not a promise of every key/backend/agent combination. Its [agent code](https://github.com/libssh2/libssh2/blob/libssh2-1.11.1/src/agent.c) supports Unix agent sockets and Windows backends including Pageant and [the OpenSSH named pipe](https://github.com/libssh2/libssh2/blob/libssh2-1.11.1/src/agent_win.c). No OpenSSH config alias or `ProxyJump` policy is supplied by these APIs; routing and trust per hop would be Imp code, with [custom stream callbacks](https://libssh2.org/libssh2_session_callback_set2.html) among the possible building blocks.
- **Streams and ownership.** Direct channels are bidirectional; [`send_eof`](https://libssh2.org/libssh2_channel_send_eof.html) says no more data will be sent and is distinct from closing the channel. Nonblocking calls can return `EAGAIN`; drive socket readiness from [`session_block_directions`](https://libssh2.org/libssh2_session_block_directions.html) and fairly service shared-session work, remaining data, and partial writes. The [Rust wrapper](https://docs.rs/ssh2/latest/ssh2/struct.Session.html) shares a session across its channels and warns that a blocking call can hold up other calls on it. Ownership can be in-process with no listener or child, but task cancellation has to retire in-flight channel state and orderly session shutdown has to be driven. It requires the same EOF, backpressure, cancellation and owner-loss evidence as russh.
- **Distribution.** The [library is BSD-3-Clause](https://github.com/libssh2/libssh2/blob/libssh2-1.11.1/COPYING); the [Rust wrapper is MIT/Apache-2.0](https://github.com/rust-lang/ssh2-rs). A linked C library/FFI and [chosen crypto backend](https://github.com/libssh2/libssh2/blob/master/docs/INSTALL-CMAKE.md) add a native build and packaging matrix: choose static/vendor or compatible system/runtime libraries, check target-specific key algorithms and notices, and account for how patches reach users. No process dependency does not mean no native dependencies.

## Defensible next step

Keep the candidate in a separate test-only crate. Use one owner, one explicit SSH host/user/port, one disposable host pin and fixture private key, and direct channels to the fixture relay—no command execution, agent/config discovery, or local TCP port for state/action. An isolated raw-stream test listener, if used, is not an authority endpoint. Only successful authenticated channels to the configured relay should supply application data; neither an occupied port nor a renderer-provided address establishes that authority. Treat session replacement as a new authority and retire old state and action work rather than falling back to another listener or reusing stale context.

Record native Windows and Linux fixture results separately: trust refusal, one authentication and independent concurrent channels, exact state/action routing and stale rejection, stream behavior, and cleanup/recovery compared with warm `-L`. A clean fixture result supports only that profile. Any broader rollout needs an explicit player-facing trust and credential lifecycle, a compatibility decision for keys/agent/certs/config/jumps, and native packaging and patch ownership; leave existing OpenSSH paths intact in the meantime.
