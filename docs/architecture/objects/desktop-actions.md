# Desktop actions

## Purpose

Imp stores operator-defined action buttons in the desktop renderer and
forwards a command only after an explicit operator click or keyboard activation.
Saved definitions are presentation-side configuration; they do not change the
Imp node, client-adapter action helper, protocol, desktop transport boundary,
or game-state model.

## Ownership

- `apps/desktop/src/lib/action/definitions.ts` owns validation and guarded
  `localStorage` persistence for `ActionDefinition` values.
- `apps/desktop/src/components/Hud.svelte` owns the current ordered definitions,
  the one pending UI invocation, result feedback, and calls the injected
  `ActionSink`.
- `apps/desktop/src/components/ActionDialog.svelte` edits the local definitions.
- `apps/desktop/src/components/ActionBar.svelte` renders the expanded Actions
  footer; `ActionsMenu.svelte` renders the Actions shortcut in both display
  modes. `Hud.svelte` renders the contextual palette and coordinates manager
  navigation.
- `apps/desktop/src/lib/action/types.ts` remains the outbound desktop boundary.
  `StateSource` remains inbound-only.

The definition `id` is local UI identity. It is generated by the WebView with
`crypto.randomUUID()` and is unrelated to relay correlation IDs.

## Persistence and validation

Definitions are stored in saved array order under `imp.actions` in local
WebView storage. New definitions append, edits retain their ID and position, and
deletes target one exact ID. At most 64 definitions are saved. Defensive loading
retains the first 64 valid, unique definitions in persisted order; malformed and
duplicate entries do not consume that capacity. Missing storage, malformed JSON,
a non-array value, and storage read failures yield an empty list without
interrupting HUD startup. A failed storage write leaves the last successfully
persisted definition array in memory and reports a local error in the management
surface; Imp does not retry the write automatically.

Labels are trimmed on save, must remain non-empty, contain no control or malformed
characters, and are limited to 64 Unicode characters. Commands are never trimmed,
normalized, split, or sanitized. They must pass the shared protocol
`isValidActionCommand()` contract: 1-512 printable ASCII characters. Intentional
leading and trailing spaces therefore round-trip unchanged, while line breaks and
other control characters are rejected.

The command strings are operator-authored local application configuration and are
stored as plaintext in WebView storage. They are not credentials managed by
Imp. Operators must not use saved actions to store passwords or other
secrets.

## Window sizing and interaction

The normal expanded HUD lays out at 320 logical pixels wide without stretching
to the viewport height. `Hud.svelte` observes the panel's intrinsic border box,
so the titlebar, vitals, optional target, Actions footer, feedback, and frame
contribute to the measured height. It rounds the height up to a whole
logical pixel, coalesces resize requests in `requestAnimationFrame`, and skips
unchanged sizes within that branch. Leaving the branch cancels any pending
frame. Expanded contextual panels are measured separately from the normal HUD.

Both action surfaces wrap feedback inside their current width. Feedback uses
its natural height up to four lines; longer diagnostics scroll within the
live region rather than pushing Manage outside the compact panel.

Compact width follows the current intrinsic HUD row within the 280-560 pixel
bounds. The compact sizing helpers floor content height at 30 pixels and bound
it to 160 pixels; an attached panel retains that width and may grow only to
the 420-pixel panel-height bound. Browser measurement observed a 30-pixel
compact row; the outer framed panel can measure 32 pixels because of
its borders.

The expanded Actions footer and both **Actions** palettes place the title
and **Manage** (`Manage actions` to assistive technology) above a
full-width wrapping list, separated from the content by a theme divider.
Manage stays outside the scroller even when no actions are saved or an action
is pending. Settings does not link to the manager.

The footer displays up to three rows of single-line buttons at the current
font size, then scrolls vertically. Long labels truncate visually but
retain their full name. An empty footer has no list or reserved list space;
the palettes instead show an empty message. Feedback remains below the
list. The action lists, feedback, manager saved list, and command textarea
use theme-matched scrollbar thumbs and tracks.

The manager measures its own content height and uses the originating HUD
width: 320 logical pixels in expanded mode, or the compact baseline captured
before replacing the palette. **Close** or **Escape** restores the originating
Actions footer or palette and focuses its Manage button. Closing the compact
palette then measures the current HUD content instead of reusing the manager width.
The management header remains draggable; its Close button, fields, buttons,
list, and scrollbar remain non-drag regions.

The keyboard-focusable Actions shortcut uses the Lucide `Swords` icon. Its
palette wraps label-sized buttons, bounds long labels to the panel width, and
scrolls vertically without widening the HUD. Opening it by keyboard focuses
its Manage button. The active icon gains a small × and the accessible name
**Close actions**; activating it again or pressing **Escape** collapses the panel
and restores focus to **Actions**. Clicking outside the compact palette dismisses
it without moving focus back.

In both display modes, **Alerts**, **Actions**, **Settings**, and **Close Imp**
keep that order and position as panels change. Select another panel shortcut
to switch directly. **Close Imp** shows an inline confirmation in the top row.
**Cancel** or **Escape** preserves the current panel and restores focus to
**Close Imp**; **Confirm** exits Imp.

## Invocation and results

Each dispatch begins with one explicit operator activation. The HUD captures the
current `HudModel.context` synchronously and passes that exact tuple and the exact
saved command to the injected `ActionSink`. A null context is rejected locally.
Feed freshness does not gate actions because an otherwise healthy idle game can
have no recent GMCP traffic. The node's exact-context broker and the selected
client adapter's final context fence remain the execution authority.

While one UI call is pending, every action button is disabled. The HUD does not
queue, retry, batch, schedule, fan out, or automatically dispatch commands.
Another click after a result, including `unknown`, is a new operator decision.

`forwarded` means that the selected client adapter reached its documented
successful local handoff. That proof is adapter-specific: TinyFugue reports it
after writing/flushing the fixed bridge line, while Mudlet reports it after the
exact-context recheck and a non-erroring `send(command, false)` call.

Neither meaning proves that the MUD server received or executed the command.
`unknown` explicitly reports uncertain delivery and that Imp did not retry.

Pending feedback stays visible until the call resolves. The `forwarded`
message is removed after three seconds, with a short fade before removal
unless reduced motion is requested. `rejected` and `unknown` feedback,
including diagnostics, stays until superseded. Older dismissal timers cannot
clear newer feedback. Results still use live announcements, and removing
successful feedback releases its space for native HUD sizing.

Persisted action definitions are reusable command templates. They are not queued
dispatches, retained action history, stored relay payloads, retries, or reconnect
resends. The Slice 7 no-replay contract is unchanged.

## Verification

Action definitions and dispatch were verified separately from the
[Slice 27 HUD](../../status.md#slice-27-implementation--in-progress)
acceptance. The operator passed 27/27 checks on published v0.5.1 (PRs 1–3)
and separately passed 17/17 on published v0.5.2 (PR 4) on their existing
Windows installation, with no adverse observations on the latter pass. PR 4's
checklist covered the three-row footer, scrolling and access to all actions,
target transitions, Manage placement and return, and themed scrollbars. These
passes remain valid for unchanged behavior; the dividers and feedback
expiration are pending separate acceptance.

The Slice 27 pixel measurements come from Chromium and isolated Windows
WebView2 mocks, not the installed-release checklist. Higher and mixed
native DPI remain unverified. Freshness design, fixed-origin desktop-edge
placement, and remaining control and placeholder contrast are deferred.

The canonical automated gate (`npm run check`) covers definition validation,
create/edit/delete persistence, the 64-definition limit, storage-write failure,
exact command text, the window sizing helpers, exact-context invocation with a
single in-flight call, and the result wording for `forwarded`, `rejected`, and
`unknown`. Those checks do not establish layout, focus, or rendered interaction
behavior; see the Slice 27 evidence for component and runtime coverage.

Earlier manual browser mock acceptance, driven through the network-free mock
sink, covered the then-current rendered surfaces: create/edit/delete through the
management dialog, bounded expanded and compact action lists, panel
coordination, focus restoration, and invocation from both modes.

Earlier Windows-native acceptance verified a clean non-maximizable Tauri launch;
expanded and compact Settings, Actions, and management sizing/restoration;
width-preserving attached panels; originating-width management; management
dragging; the bounded wrapped compact palette and icon trigger; keyboard
Tab/Enter/Escape paths and focus restoration; create/edit/delete persistence;
native restart persistence; and exact leading/trailing command spaces across a
restart.

The post-PR #6 Windows-native smoke re-smoked the runtime-measured action
strip, revised Settings sizing, panel-dismissal behavior, icon-button focus
state, and compact/expanded panel behavior. It also covered theme switching,
native sizing, dragging, and non-maximizable behavior. It did not re-run live
action delivery; the earlier live action evidence remains valid and separate
below.

Earlier TinyFugue live action acceptance sent `look` from the native UI through
the real `RelayActionSink`, node, TinyFugue helper, and MUD path. It executed
exactly once. Removing the matching TinyFugue consumer caused a later action to
be rejected without execution; restoring the consumer did not replay that
rejected action.

Slice 16 additionally live-verified Mudlet trusted actions. A real `look`
traversed the node and Mudlet helper/Lua final hop, passed the exact-current
context check, and reached the MUD. Remote Mudlet-backed action delivery was
also exercised through SSH and authenticated WSS.

Across both client adapters, no queue, automatic retry, replay, reconnect
resend, or duplicate invocation was observed.

Deterministic tests cover the `unknown` result semantics and its no-retry
wording, and manual browser mock acceptance checked that presentation. No live
`unknown` result was deliberately manufactured.

Slice 11 transport acceptance re-verified the same real outbound `look` action
from the native Windows UI through authenticated Direct WSS. After a deliberate
gateway interruption, the desktop reconnected automatically and another action
succeeded. Restoring the previous managed-SSH configuration then re-verified
state and action delivery without changing relay or feed configuration.
